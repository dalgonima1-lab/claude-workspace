작성일: 2026-11-23
전제 문서: `notes/사업비서-앱-대화정리.md`
상태: 설계 초안. 사용자 확인 후 코드 작성 시작

---

## 1. 사용자 맥락

| 항목 | 내용 |
|---|---|
| 사용자 | 제이피앤텍 대표 |
| 병행 업무 | 서일이앤씨 업무 |
| 주요 발주처 | 서울교통공사 (역사, 전기사업소, 본사 부서 단위로 담당자 다수) |
| 납품 품목 | 전력감시시스템, 조명제어시스템 |
| 협력업체 | 알트에이 (설치, 시공, 자재 등 협업 추정) |
| 구독 | Claude Max → 월 100달러 API 크레딧으로 운영 (추가 비용 0) |

설계에 미치는 영향 세 가지:
1. **소속이 둘**이다. 모든 기록에 "제이피앤텍 / 서일이앤씨" 태그가 붙어야 하고, 공유 수신 시 기본 소속을 고르거나 AI가 추정한다.
2. **공공기관 납품 업종**이라 일반 영업보다 "장애 접수, 점검, 검수, 서류 제출, 기성 청구, 하자보수" 같은 사건 유형이 핵심이다.
3. **상대가 세 부류**다. 발주처(서울교통공사 담당자), 협력업체(알트에이), 자재·외주업체. 같은 통화라도 누구와 했느냐에 따라 할 일의 담당자가 달라진다.

## 2. 업무 흐름과 사건 유형

### 2-1. 사업 한 건의 수명 주기
문의·현장조사 → 견적·입찰 → 계약 → 자재 발주 → 제작·설치 → 시운전·검수 → 준공·납품 → 대금 청구(기성, 세금계산서) → 하자보수 기간(장애 접수, 정기 점검)

### 2-2. AI가 분류할 사건 유형 (record.type)

| 코드 | 유형 | 예시 | 기본 후속 동작 |
|---|---|---|---|
| `fault` | 장애·AS 접수 | "○○역 조명제어 안 됨, 내일 와 달라" | 긴급도 티켓 생성 + 방문 일정 |
| `inspection` | 정기·수시 점검 | "다음 주 전력감시 점검 날짜 잡자" | 일정 등록 |
| `delivery` | 납품·설치·시운전 일정 | "자재 15일 입고, 설치 20일" | 일정 2건 + 자재 할 일 |
| `acceptance` | 검수·준공 | "검수는 금요일 10시 전기사업소" | 일정 + 준비물 할 일 |
| `document` | 서류 제출 | "시험성적서, 준공도서 이달 말까지" | 기한 할 일 |
| `quote` | 견적·입찰 | "조명제어 추가분 견적 요청" | 견적 할 일 + 금액 기록 |
| `contract` | 계약·변경 | "계약 변경 건 도장 받으러 와라" | 일정 또는 할 일 |
| `payment` | 대금·기성·세금계산서 | "기성 청구서 올려라, 25일 지급" | 받을 돈 기록 + 기한 |
| `material` | 자재·외주 발주 | "알트에이에 케이블 100m 추가 요청" | 상대 담당 할 일 |
| `nightwork` | 야간 작업·출입 허가 | "야간 작업 허가서 내고 23시 진입" | 일정 + 서류 할 일 |
| `meeting` | 회의·방문 약속 | "수요일 본사 회의" | 일정 |
| `info` | 단순 정보 공유 | 참고 사항 | 기록만 |
| `personal` | 사업 무관 | 가족, 지인 | 저장 안 함 (설정에 따라) |

### 2-3. 추출 항목 (AI 응답 JSON)

```json
{
  "is_business": true,
  "entity": "제이피앤텍 | 서일이앤씨 | 불명",
  "counterpart": {
    "org": "서울교통공사 ○○전기사업소",
    "org_kind": "client | partner | vendor | other",
    "person": "김 과장",
    "phone": null
  },
  "project": "○○역 조명제어 교체",
  "system": "power_monitoring | lighting_control | both | none",
  "site": "○○역",
  "type": "fault",
  "urgency": "high | normal | low",
  "summary": "한 줄 요약",
  "decisions": ["결정 사항 1"],
  "events": [{"title": "○○역 장애 점검 방문", "start": "2026-11-25T10:00", "end": null, "place": "○○역 역무실"}],
  "tasks": [{"title": "시험성적서 제출", "owner": "me | counterpart | partner", "due": "2026-11-30", "note": null}],
  "money": [{"kind": "receivable | payable | quote | contract", "amount": 3500000, "due": "2026-12-25", "note": "11월 기성"}],
  "reply_draft": "확인 문자 초안",
  "sensitive": false
}
```

Claude 구조화 출력(`output_config.format`)으로 이 스키마를 강제한다. 날짜는 통화 시각 기준 상대 표현("내일", "다음 주 금요일")을 절대 날짜로 바꿔 넣는다.

## 3. 데이터 모델 (폰 로컬 DB, Room)

```
entity        내 소속: 제이피앤텍, 서일이앤씨
org           상대 조직: 이름, 종류(client/partner/vendor/other), 상위 조직(서울교통공사 → 사업소)
contact       담당자: 이름, 직함, 전화, 소속 org, 폰 연락처 ID
project       사업·현장: 이름, entity, 발주처 org, 시스템 종류, 상태(견적~하자보수), 하자보수 종료일
record        기록 1건: 원문, 출처(call/sms/kakao/mail/visit/memo), 발생시각, entity, org, contact, project,
              type, urgency, summary, decisions(JSON), 원본 AI 응답(JSON), sensitive 여부
event         일정: record 연결, 제목, 시작·종료, 장소, 삼성 캘린더 event_id (동기화 추적용)
task          할 일: record 연결, 제목, 담당(me/counterpart/partner), 기한, 완료 여부, 알림 시각
money         금전: record 연결, 종류(receivable/payable/quote/contract), 금액, 기한, 정산 여부
ticket        장애·AS: record 연결, 현장, 시스템, 증상, 긴급도, 상태(접수/방문예정/조치중/완료), 완료 시각
```

- 모든 테이블에 `entity_id`가 있어 소속별 필터가 된다.
- `ticket`은 `type = fault`인 record에서 자동 생성한다. 유지보수 업종이라 1단계에 포함하는 것을 권장한다.
- 폰 로컬이 원본이고, 구글 드라이브 백업과 PC 열람은 3단계.

## 4. 화면 설계

### 4-1. 커버 화면 (접힌 상태, 세로 길쭉)
- 상단: 소속 전환 칩 (제이피앤텍 | 서일이앤씨 | 전체)
- "확인 대기" 카드: 분석은 끝났는데 아직 승인 안 한 건 (가장 위)
- 오늘 일정 3건, 기한 임박 할 일 3건, 미완료 장애 티켓 수
- 하단 큰 버튼 하나: "직접 입력" (음성·텍스트)

### 4-2. 펼친 화면 (2단 분할)
- 왼쪽 패널: 탭 4개 — 거래처 / 사업 / 할 일 / 장애
  - 거래처: 조직 → 담당자 트리. 마지막 연락일 표시, 오래된 순 정렬 옵션
  - 사업: 상태별 그룹 (진행 / 하자보수 중 / 종료)
  - 장애: 긴급도·상태별 보드
- 오른쪽 패널: 선택한 항목의 타임라인. 기록 카드에 원문 펼치기, 연결된 일정·할 일·금전 표시

### 4-3. 공유 수신 → 확인 카드 화면
1. 공유로 텍스트가 들어오면 즉시 "분석 중" 화면 (원문 표시)
2. 결과 확인 카드: 소속, 상대, 사업, 유형, 요약은 드롭다운·텍스트로 수정 가능
3. 일정·할 일·금전 항목은 각각 체크박스. 끄면 등록 안 함
4. 하단: [등록] [답장 초안 보기] [사업 무관으로 버리기]
5. 플렉스 모드(반 접힘): 위쪽 화면에 카드 내용, 아래쪽 화면에 수정 필드와 버튼

### 4-4. 설정
- 기본 소속, 소속 자동 추정 여부
- 민감 연락처·키워드 목록 (AI 전송 제외)
- 발주처·협력업체 연락처 그룹 지정 (해당 번호는 무조건 사업으로)
- 캘린더 선택 (삼성 캘린더 계정 중 어느 것에 쓸지)
- 모델 선택 (Opus 5.5 / Haiku 5.5), 중계 서버 주소

## 5. 중계 서버 (Vercel, Node/TypeScript)

- `POST /analyze` : `{ text, source, received_at, default_entity, known_orgs[], known_projects[] }` → 2-3절 JSON
  - 모델 `claude-opus-5-5`, 구조화 출력, 시스템 프롬프트에 업종 맥락(서울교통공사 납품, 두 소속, 알트에이 협력) 고정
  - 알려진 거래처·사업 목록을 함께 보내 이름 매칭 정확도를 높인다
- `POST /draft-reply` : 기록 → 확인 문자 초안
- `POST /brief` (2단계) : 오늘 일정·할 일·티켓 → 아침 브리핑 문장
- 인증: 앱과 서버가 공유하는 비밀 토큰 1개 (헤더). Claude API 키는 서버 환경 변수에만 존재
- 로그에 통화 원문을 남기지 않는다

## 6. 1단계 범위 (제안)

1. 공유 수신 (통화 요약, 문자, 카톡 텍스트)
2. 중계 서버 분석 + 확인 카드
3. 거래처·사업·기록 타임라인 (펼친 화면 2단)
4. 삼성 캘린더 일정 등록 + 할 일 + 기한 전날 알림
5. **장애·AS 티켓** (업종 특성상 추가 권장)
6. 소속 2개 전환, 민감 연락처 제외

2단계로 미룸: 명함·영수증 촬영, 미수금 대조, 아침 브리핑, 답장 초안 전송, 알트에이 공유용 보고서

## 7. 사용자 확인 필요

1. 1단계에 장애·AS 티켓을 넣는 것에 동의하는지
2. 소속 구분이 "제이피앤텍 / 서일이앤씨" 두 개로 충분한지, 서일이앤씨 쪽도 서울교통공사 납품인지
3. 알트에이와 공유해야 하는 정보가 있는지 (있으면 2단계에 "협력사 공유 보고서" 추가)
4. 통화 요약 샘플 1개 (없으면 위 업종 기준 가상 샘플로 개발 시작 후 실제 샘플로 교정)

## 8. 디자인 방향 v2 (2026-11-23, "자비스처럼")

사용자 요청: AI가 돌아가는 느낌, 자비스 같은 비서.
콘셉트: **제어실 화면 위에서 비서가 말을 거는 느낌.** 전력감시 SCADA 화면의 어두운 남청 바탕을 빌리고, 비서의 목소리(청록)가 상황을 한 문장으로 말한다.

### 토큰
| 역할 | 값 |
|---|---|
| 바탕 Ground | #0B1A2E (검정이 아닌 또렷한 남청) |
| 패널 Panel | #112640 |
| 선 Line | #1E3A5C |
| 글자 Text / Muted | #E8EFF7 / #8DA2BA |
| 비서 목소리·살아 있는 표시 Signal | #5CD6E6 (이 용도에만 사용) |
| 주의 Amber | #F2B544 |
| 긴급 Red | #FF6B6B |
| 돈·완료 Green | #4CD38A |

서체: Pretendard (OFL). 큰 시각·숫자는 Light 300에 tabular 숫자, 본문 Regular 15, 라벨 Medium 12, 제목 SemiBold.

### 구조 원칙
- 모든 화면 맨 위에 **비서 띠**: 가는 고리 표식 + 데이터로 만든 한두 문장 ("오늘 일정 3건이 있습니다. 다음은 15:00 알트에이 통화입니다.")
- 카드 격자 대신 **세로 레일**(가는 선 + 점)로 일정·할 일·기록을 흐르게 배치. 테두리 카드 최소화.
- 분석 화면은 **전사본을 청록 선이 훑어 내려가고** 단계 안내가 진행되는 장면. 앱에서 가장 기억에 남는 한 장면으로 여기에만 움직임을 쓴다.
- 아래 입력줄 "무엇을 정리할까요?"가 비서에게 말을 거는 자리.
- 피한 것: 가운뎃점 나열, 대문자 라벨, 화살표 버튼, 모든 요소에 테두리, 그라데이션.
